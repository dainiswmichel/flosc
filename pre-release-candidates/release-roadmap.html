What this document is, and the standard it holds itself to

Every figure below was measured in this repository on the date stamped above, against the built zip that would actually be uploaded — not against the source tree. That distinction is the whole reason the previous rounds went wrong, and it is restated in §3 because it changes the numbers materially.

Where something has not been established, it says so rather than leaving a gap the reader fills in optimistically. A static-analysis PASS is not a completed repair.

3. The measurement that changes the numbers

Scan what ships, never the source tree

Run against the source tree, wporg-audit.sh reports 11 pass / 6 fail / 5 read. Run against the extracted v113 zip, it reports 12 pass / 5 fail / 5 read.

The difference is tests/, which .distignore correctly excludes from the artifact. The audit was counting test fixtures as shipped violations.

unzip -q pre-release-candidates/claude-opus-5/flosc.zip -d /tmp/ship
./wporg-audit.sh /tmp/ship/flosc

This is the same failure mode as the phpcs.xml.dist exclude-pattern that makes an in-place scan match zero files and exit clean in 90ms. Measure the artifact, or the number means nothing.

The instrument itself is a blocker

An audit that reports four false failures out of five teaches its reader to skim past FAIL. That is precisely how a stripped tree reached five review rounds looking clean. Fixing the comment-matching is not cosmetic housekeeping — it is what makes the remaining number trustworthy enough to gate a submission on.

6. The route

Phases are numbered because they are a genuine dependency chain: each one's output is the next one's input. Phase 0 gates everything, and it is not mine to complete.

PHASE 0Owner decisionsBLOCKING
  • Approve the v114 scope before any plugin code is written.
  • Supply the fatal's error text — debug.log or the WSOD message from the test site. v113 removed a mechanism that produces that screen; it was never shown to be the one. Without the text, any further work on it is hypothesis against a live site, which is what v111–v113 already cost.
  • Rule on the repo-root tree — see Phase 6.
PHASE 1Make the instrument trustworthySMALL
  • Teach wporg-audit.sh to skip comment lines, so a FAIL means a finding.
  • Default its target to the extracted zip rather than the source tree.
  • Add a negative control: plant a known violation, confirm it is reported, remove it. A clean scan is only evidence when the scan can fail.

Candidate-level tooling only. No file inside the plugin tree changes, so this cannot regress the product.

PHASE 2Close the two real findingsREQUIRED
  • External Services in readme.txt — every outbound host named, with purpose and privacy policy. Raised every round; the cheapest rejection to stop having.
  • class-oauth2-handler.php:537 — stop deriving the SSO callback host from the request. Prefer the flow's stored custom domain; where the request must be consulted, validate against a configured allowlist rather than sanitizing and trusting.
PHASE 3Work the five judgement itemsREADING
  • Read all seven callbacks in §5 and escape their return values.
  • Validate the decoded structure at the json_decode site.
  • Draft the reply-email justification for the 16 user-creation incidences.
PHASE 4Build the gate the policy already promisesBLOCKING #1
  • Write flosc-gate.sh, or amend the policy to name the scripts that exist. Right now the release bar cites a script that is not in the tree, so bar item 1 can never be satisfied as written.
  • Create build/evidence/ and have the gate write gate output, phpcs reports and the zip sha256 into it.
  • Run parity-gate.sh against v87 so the candidate is proved complete by inventory, not by diff.
PHASE 5Runtime verification — the part no static tool can doBLOCKING #5

7. What this document does not establish

  • No WordPress runtime was available. The plugin was not activated, no admin screen was rendered, no navigation was exercised. Every Phase 5 row is unexecuted.
  • Plugin Check has not been run on v113. It needs wp-cli and a booting WordPress.
  • phpcs and PHPCompatibilityWP were not re-measured on the v113 zip for this document. The figures quoted in §2 are from v95–v97 and are marked RE-MEASURE for that reason.
  • The fatal reported on the test site is undiagnosed. No error text was ever obtained and it has never reproduced in a build container.
  • The seven callbacks in §5 have not been read. They are listed because the audit surfaced them, not because their escaping has been assessed.

One candidate, one claim

Each version above changes one thing and says so in its title. The rounds that went wrong were the ones where a round's stated purpose and its actual diff were different sizes — a branding cleanup that also renamed live member roles, a nesting fix measured with a metric that passed while the panel held a blog post. Scope stated in the title, measured on the artifact, with the unverified listed by name.
