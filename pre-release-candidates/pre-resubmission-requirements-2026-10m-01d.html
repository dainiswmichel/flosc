2. A real defect in v114 — the starter-pack flush does not do what its comment claims

Verified from source, and it matters

v114's starter-pack installer carries this:

// The newly registered flow must be routable immediately.
if ( function_exists( 'flush_rewrite_rules' ) ) {
    flush_rewrite_rules( false );
}

It does not make the new flow routable. The sequence:

  1. add_rewrite_rules() is hooked to init (class-flosc-framework.php:1964). It globs *_ivr.md from disk and calls add_rewrite_rule(…, 'top') for each one it finds, populating $wp_rewrite->extra_rules_top.
  2. The pack installer runs later in the same admin request, after init is finished. It copies the new flow_ivr.md to disk, writes the flow option, then flushes.
  3. flush_rewrite_rules() rebuilds from the in-memory extra_rules_top that was populated at init — before the new file existed — and writes that to the rewrite_rules option.

So the option saved by those four lines is the rule set from the start of the request, still missing the new slug. Nothing calls add_rewrite_rules() again after the file lands.

The fresh-install case is actually rescued by something else: the priority-1 handle_app_route added in the same round. detect_flow_from_request_route() re-globs IVR files from disk and preg_matches each flow's slug against REQUEST_URI directly — it never consults the saved rewrite rules. That is what answers the URL before core's canonical guessing can 301 it to a similarly named post.

Why this is dangerous rather than merely untidy

The comment asserts an invariant the code does not establish, and the real load-bearing mechanism (the priority-1 route) is documented nowhere as load-bearing. The next agent reads "the newly registered flow must be routable immediately", believes the installer handles it, refactors or re-prioritises handle_app_route, and the fresh-install 301 returns — with a passing test suite, because the committed contract test only asserts that the hook is registered at priority 1, not why.

This is the same failure shape as my v110: a true-sounding claim attached to code that does not deliver it, with the actual behaviour resting elsewhere.

Proposed fix (v115, small): re-scan before persisting, so the saved option is correct and the priority-1 route stops being the only thing holding the case up.

// extra_rules_top was built at init, before this pack's file existed on disk.
// Re-scan now, then persist, or the saved option omits the new slug and the
// priority-1 route in handle_app_route() is the only thing answering the URL.
flosc()->add_rewrite_rules();
flush_rewrite_rules( false );

The same shape exists in the older flush on the flow upload screen (admin/ivr-upload-handler.php) and should be checked at the same time. Neither is a resubmission blocker — the route works — but both are traps, and a trap that reads as a fix is how five days got lost last time.

4. The gate list — what must be true before the zip is uploaded

A. Product gate (new, and non-negotiable)

The browser matrix must assert the panel contains a working chat — chat input present, document is the FLOSC app — on the exact zip being submitted. Frame depth and bubble count are the metrics that certified a broken product in v110; they must never again be the pass condition.

  • Fresh WordPress, install the Vegan Latvian Kitchen pack, open the bubble on a post. Assert chat input.
  • Repeat without visiting Settings → Permalinks, which is the condition that produced the original 301.
  • Log in from inside the panel; assert the panel still holds chat afterwards.
  • Click Minimize from the full page; assert hub at depth 0, chat at depth 1.
  • Force a non-FLOSC page into the frame; assert the error message appears and no website renders.

B. WordPress.org gate — two real findings, measured on the shipped zip

Audited against the extracted artifact, not the source tree (in-tree scans count tests/ as shipped violations and inflate the count):

  • readme.txt External Services section. Raised in every round T7–T13. v114's readme.txt now carries 16 numbered entries with no gaps — this appears closed, and the gate suite confirms it. Re-verify on the final zip.
  • includes/sso/class-oauth2-handler.php:537 — the SSO callback host is still derived from $_SERVER['HTTP_HOST'], a client-supplied header. T12 named this specifically. sanitize_text_field() does not make it trustworthy. Prefer the flow's stored custom domain; validate against a configured allowlist where the request must be consulted.

C. Human-judgement items — for the reply email, not the diff

  • Seven shortcode and the_content callbacks must escape everything they return. A grep cannot decide this; each must be read.
  • One json_decode( stripslashes( … ) ) site needs its decoded structure validated.
  • 16 incidences of creating or logging in users (magic links, SSO, post-purchase). Not a bug — a design decision the reviewer accepts only with written justification.

D. Evidence gate — currently unsatisfiable as written

  • WORDPRESS-ORG-RELEASE.md requires flosc-gate.sh to report RESULT: all gates PASS. No such script exists. Present are tests/flosc-check.sh, tests/verify-standards.sh, wporg-audit.sh, parity-gate.sh. Either write the gate or amend the policy to name what exists.
  • No build/evidence/ directory. The eight-row manual matrix has never been recorded with dates and a signature.
  • Official Plugin Check has never been run on any candidate. It needs wp-cli and a booting WordPress.

The historical state of the production rewrite-rules option is not in source control.

6. The process change that would have prevented all of this

Four rules, each one bought with a specific failure

  1. Write the contract before the fix. Name the user-visible invariant in one sentence — "the panel contains a working chat" — and let it decide what the test asserts. v110 failed because I picked the metric after choosing the fix, so the metric could only confirm me.
  2. A test that has never failed is not a test. Break it on purpose, watch it go red, restore it. Report the negative control alongside the pass. v111 did this and immediately exposed v110 as false.
  3. Reproduce before repairing; when the root cause appears, revert and re-approach from the baseline. At v111 the 301 was on the table and v109/v110 were still in the tree. The correct move was to drop them and retest the minimal repair against v107. v114's rebuild-from-v107 is that move, taken three rounds late.
  4. A defect found is not a defect authorised. Finding something true during a release freeze produces a line in a findings list, not a commit. The decision belongs to the project manager.

7. Recommended order

v115 — the rewrite-rescan fix from §2, plus the same check on ivr-upload-handler.php. One scope, one claim.

v116 — the SSO HTTP_HOST fix from §4B, and the callback-escaping read from §4C.

v117 — flosc-gate.sh and build/evidence/, so §4D becomes satisfiable.

Then the product gate §4A — a signed, dated browser campaign on a real install. Not a candidate. Nothing in any container can substitute for it.

Then submit, with the reply email carrying §4C's justifications and a point-by-point map from each T7–T13 finding to its fix.
