1. Why 190 versions did not converge

Two mechanical reasons, both visible in the review email itself.

The abstractions are unreviewable. Every flagged category is a case where a security operation sits behind an indirection: flosc_capture_output( static function () { ?> … <?php } ) for output, wp_unslash( $_POST ) followed by flosc_submitted_fields_are_text() for input, and filter_var( …, FILTER_CALLBACK, array( 'options' => 'flosc_sanitize_…' ) ) for sanitising. These may be functionally correct. They are invisible to the tools that decide the review. PHPCS sniffs and the Plugins Team's analysis both match patterns at the call site; one function of indirection and the protection cannot be seen. The same abstraction is therefore re-flagged in every round, regardless of how many individual items were repaired in that round.

The unit of work was wrong. The email reports "out of a total of 43 incidences", "out of a total of 47 incidences", "out of a total of 30 incidences", and shows roughly eight examples of each. Its own checklist states the reason: "the Plugins Team may not share all cases of the same issue." Repairing the eight reported items yields a version that still contains thirty-nine instances of the same defect. The next round shows eight more. Isolating and repairing each reported item cannot converge; the arithmetic forbids it. The unit of work has to be the class of defect, eliminated exhaustively across the whole tree and counted to zero.

Consequence for how claims should be read. "Tested locally and working" can be true and still worthless here, because local testing measures whether the plugin functions and the review measures whether the code is reviewable. Those two properties can diverge completely. A version that works perfectly is fully consistent with a version that is rejected. No amount of additional functional testing closes that gap, which is why testing locally did not prevent the outcome.

Two traps worth knowing, because both have produced false green results:

  • A PHPCS ruleset file containing an illegal -- inside an XML comment makes PHPCS fail to parse and report nothing, which reads exactly like a clean pass. Prove the ruleset works by running it against a deliberately bad one-line file and confirming it reports violations.
  • php script.php | tail -1 reports the exit status of tail, not of PHP. A test script that fatals can be recorded as passing. Any runner that pipes its checks is not trustworthy until its failure path has been exercised on a deliberately broken copy.

3.5 TSV formula injection — one incidence, a genuine bug

Flagged at includes/class-flosc-framework.php:13036. Untrusted chat text is written to TSV without neutralising spreadsheet formula prefixes, so a visitor can get a formula to execute when the export is opened.

Fix. Neutralise in one place, applied to every cell:

/**
 * Keep an exported cell from being read as a spreadsheet formula.
 *
 * @param string $value Cell value.
 * @return string
 */
function flosc_tsv_cell( $value ) {
	$value = (string) $value;

	if ( '' !== $value && in_array( $value[0], array( '=', '+', '-', '@', "\t", "\r" ), true ) ) {
		$value = "'" . $value;
	}

	return str_replace( array( "\t", "\r", "\n" ), ' ', $value );
}

Proof. Export a conversation whose message text is =1+1 and confirm the cell shows the literal text rather than 2.

4. The instruction set that makes a false claim structurally hard

This addresses the stated problem directly: not how to trust an agent, but how to make trust unnecessary. Give any agent working on FLOSC these rules, and refuse work that does not satisfy them.

  1. No security operation may sit more than zero function calls from the thing it protects. Escaping goes on the echo line. Sanitising goes on the read line. No helper, no wrapper, no callback. If a reviewer's static analyser cannot see it, it does not count, regardless of whether it works.
  2. Fix classes, never reported instances. Every repair is followed by a grep across the whole tree for the same pattern, and the grep count must reach zero. The reviewer shows you eight of forty-seven on purpose.
  3. Zero suppressions. No phpcs:ignore, no phpcs:disable, no exclusions, no weakened test, no narrowed ruleset. A suppression reads to a reviewer as a concealed finding, which is the specific accusation already on the table.
  4. Every claim arrives with the command that produced it and its verbatim output. Not "WPCS passes" but the command and the summary line it printed. A claim without a reproducible command is not a claim.
  5. "Not run" is never reported as "passed." Checks that were not executed are listed as not executed. Runtime reproduction, static inspection, and inherited claims are named separately and never merged.
  6. A check's failure path must be exercised before its success is believed. Point each tool at a deliberately broken copy and confirm it reports the breakage. A green result from a check that has never failed is not evidence.
  7. The acceptance gate is the five commands in section 2, run against the directory that will be zipped — not against a working copy, a candidate, or a branch.

5. What this plan does not do

  • It does not guarantee approval. Passing every technical check does not establish that the reviewer will accept the programmatic-login justification, and section 3.3 remains the open risk.
  • It is not based on reading the FLOSC code. Every count is the reviewer's. The file and line references are the ones the email supplies. Actual totals may be higher, and section 1 explains why they probably are.
  • It does not estimate effort. Section 3.1 and 3.2 are large mechanical passes across the admin directory and the framework file; 3.3 is a product decision; 3.4 needs real legal entity names and working links that no agent should invent; 3.5 is small.
  • Nothing in this entry has been tested. It is a plan, and it is labelled as one.

Issue text, unmodified

When you link to the Ajax endpoint, you cannot assume that it's always located at wp-admin/admin-ajax.php. There are different configurations in which that won't work.

This means you can't link it statically, you have to use a function to determine its location, for example: admin_url( 'admin-ajax.php' );

Obviously you would need to execute that call on PHP and then pass the information to your JS file, you can do that using the wp_localize_script() function which is also useful for other uses like passing the nonce. Let me share an example:

function floscb_scripts() {
wp_enqueue_script( 'floscb-script', FLOSCB_PLUGIN_URL . 'js/script.js', array(), FLOSCB_VERSION );

  'ajax_url' => admin_url('admin-ajax.php'),
  'nonce'  => wp_create_nonce( 'floscb-ajax-nonce' ),
));
}
add_action( 'wp_enqueue_scripts', 'floscb_scripts' );

Once you have this, you can later refer to your Ajax endpoint in the JS file by using the floscb-ajax.ajax_url variable. Please refer to the Ajax documentation: https://developer.wordpress.org/plugins/javascript/ajax/

Plugins are permitted to require the use of third party/external services as long as they are clearly documented.

When your plugin reach out to external services, you must disclose it. This is true even if you are the one providing that service.

To do this, you must update your readme file to clearly explain that your plugin relies on third party/external services, and include at least the following information for each third party/external service that this plugin uses:
What the service is and what it is used for.
What data is sent and when.

Remember, this is for your own legal protection. Use of services must be upfront and well documented. This allows users to ensure that any legal issues with data transmissions are covered.

🔴️ Data Must be Sanitized, Escaped, and Validated Issue10

When you include POST/GET/REQUEST/FILE calls in your plugin, it's important to sanitize, validate, and escape them. The goal here is to prevent a user from accidentally sending trash data through the system, as well as protecting them from potential security issues.

SANITIZE: Data that is input (either by a user or automatically) must be sanitized as soon as possible. This lessens the possibility of XSS vulnerabilities and MITM attacks where posted data is subverted.

VALIDATE: All data should be validated, no matter what. Even when you sanitize, remember that you don’t want someone putting in ‘dog’ when the only valid values are numbers.

ESCAPE: Data that is output must be escaped properly when it is echo'd, so it can't hijack admin screens. There are many esc_*() functions you can use to make sure you don't show people the wrong data.

To help you with this, WordPress comes with a number of sanitization and escaping functions. You can read about those here:

https://developer.wordpress.org/apis/security/sanitizing/
https://developer.wordpress.org/apis/security/escaping/

Remember: You must use the most appropriate functions for the context. If you’re sanitizing email, use sanitize_email(), if you’re outputting HTML, use wp_kses_post(), and so on.

An easy mantra here is this:

Sanitize early
Escape Late
Always Validate

Clean everything, check everything, escape everything, and never trust the users to always have input sane data. After all, users come from all walks of life.

🔴️ Variables and options must be escaped when echo'd Issue11

Much related to sanitizing everything, all variables that are echoed need to be escaped when they're echoed, so it can't hijack users or (worse) admin screens. There are many esc_*() functions you can use to make sure you don't show people the wrong data, as well as some that will allow you to echo HTML safely.

At this time, we ask you escape all $-variables, options, and any sort of generated data when it is being echoed. That means you should not be escaping when you build a variable, but when you output it at the end. We call this 'escaping late.'

Besides protecting yourself from a possible XSS vulnerability, escaping late makes sure that you're keeping the future you safe. While today your code may be only outputted hardcoded content, that may not be true in the future. By taking the time to properly escape when you echo, you prevent a mistake in the future from becoming a critical security issue.

This remains true of options you've saved to the database. Even if you've properly sanitized when you saved, the tools for sanitizing and escaping aren't interchangeable. Sanitizing makes sure it's safe for processing and storing in the database. Escaping makes it safe to output.

Also keep in mind that sometimes a function is echoing when it should really be returning content instead. This is a common mistake when it comes to returning JSON encoded content. Very rarely is that actually something you should be echoing at all. Echoing is because it needs to be on the screen, read by a human. Returning (which is what you would do with an API) can be json encoded, though remember to sanitize when you save to that json object!

There are a number of options to secure all types of content (html, email, etc). Yes, even HTML needs to be properly escaped.

https://developer.wordpress.org/apis/security/escaping/

Remember: You must use the most appropriate functions for the context. There is pretty much an option for everything you could echo. Even echoing HTML safely.
