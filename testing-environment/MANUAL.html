01 What this is for

Plugin Check was clean on all five rejected submissions.

So Plugin Check alone is not the instrument. This bench exists so that you can see the findings yourself, before you upload — and so that a coding tool’s claim of “green” can be checked rather than believed. Including mine.

It is agent-neutral by construction. Nothing in the runner knows which tool wrote the code it is measuring:

02 Install it, once

One paste, ending in a self-check.

It finishes by running doctor, so the first thing you see is the state of the environment rather than a claim about it.

The line people skip

The allow-plugins.dealerdirect line is not cosmetic. Without it composer installs WPCS but never registers the standard, and every --standard=WordPress run exits 3 — which looks exactly like exit 0 unless something is watching for it. doctor watches.

03 The procedure you run

Three commands, in this order, every time.

A new terminal opens in your home directory, so the cd is not optional — without it zsh says no such file or directory: ./flosc-test.

What you can point at

The zip form is the one that settles an argument. It is the same file WordPress.org received, so nothing can differ between what you tested and what you uploaded.

The tilde trap

~ already means /Users/dainismichel. Writing ~/Users/dainismichel/… expands to /Users/dainismichel/Users/dainismichel/… and fails. Use one or the other, never both.

One procedure at a time

--cmd is how you get the exact phpcs line to paste into your own shell. A --cmd run never reports a failure — it ran nothing.

How a run ends

One of two lines, plus a transcript in testing-logs/ named with the UTC timestamp and the target path, so two runs can be diffed:

ALL PROCEDURES RUN, NOTHING FAILED. SOMETHING FAILED OR DID NOT RUN. Read the blocks above; exit 1.

Every command

CommandWhat it does
./flosc-testusage, the candidate list, the procedure list
./flosc-test whatwhat the suite checks and what it does not
./flosc-test doctorcheck the environment, report, change nothing
./flosc-test doctor --fixalso start wp-env, install Plugin Check, create the fixture post

05 Why you never type the plugin directory

Two functions do it for you.

You type codex-gpt5, or a directory, or a zip. You never type …/flosc-by-codex-gpt5/flosc.

First: what you pointed at

Three branches, in order — is it a file ending .zip, is it a directory, is it a folder name inside pre-release-candidates. The third branch is why the bare name works.

Second: finding the plugin inside it

It looks for a .php file whose line starts with Plugin Name: — optionally behind a *, because it is usually inside a docblock. That is the same thing WordPress itself looks for. It checks the directory you gave it, then searches three levels down, skipping vendor and node_modules.

So pre-release-candidates/grok-4-6 resolves to pre-release-candidates/grok-4-6/flosc-by-grok-4-6/flosc without you knowing the layout.

There is no hidden state

The target used to live in a hidden .flosc-candidate file that every command read silently. The comment above the code says why that was wrong:

select still exists, but it only writes a default, and a run that falls back to it says so on screen every time:

WARNING: no target given, so a REMEMBERED one from .flosc-candidate is being used. directory /Users/.../flosc-by-codex-gpt5/flosc Name it on the command line instead: ./flosc-test all <candidate|zip>

06 The ship tree

This is the single most important decision in the file. The first local Plugin Check run was pointed at a working directory and returned hundreds of findings in tests/, .github, handoff.md and build-dist-zip.sh — not one of which is in the zip WordPress.org receives.

07 Exit codes, and NOT RUN

A check that did not run never prints zero.

Three functions do all the reporting. RC is the run’s own exit code.

notrun is used when a check could not execute — a missing tool, a stopped container, no ship tree. It sets RC=1 exactly like a failure, because a check that did not run is not a pass.

Three possible endings

EndingMeaning
---- exit 0 ----ran, nothing found
---- exit 1 ----ran, findings above
NOT RUNdid not execute. Fix the reason, re-run.

Why PHPCS gets special handling

PHPCS exits 3 when it cannot run at all — for example when the WordPress standard was installed but never registered. Exit 3 was being read as “not 1, therefore fine”.

phpcs exitMeaning
0ran, nothing found
1 or 2ran, findings
3+did not run — standard missing, bad config

Procedure 10Plugin CheckWordPress.org’s own tool, in wp-env

Three defences, each from a real failure

  • The fixture post. Plugin Check’s runtime checks ask WordPress for a post permalink. With no published post the run aborts with Error: Unable to retrieve post URL for post type: post, exit 1, having checked nothing. That is the fixture, not the plugin. The procedure supplies the post.
  • The exit code is not the verdict. wp-cli exits 0 whether Plugin Check found nothing or found fifty errors. Reading its exit code printed ---- exit 0 ---- under a screen of ERRORs. The ERROR and WARNING rows are counted instead.
  • The stale-mount guard. wp-env serves whatever directory it was started with. Change .wp-env.json without restarting and the container keeps serving the old path. Any finding naming tests/, handoff, .github, .gitignore, .distignore or build-dist-zip.sh means exactly that, and the procedure says so with the fix instead of printing false findings.
Procedure 11Clean install, WP_DEBUG onwp-env + wp-cli + HTTP

WordPress.org’s submission checklist says: “I tested my updated plugin on a clean WordPress installation with WP_DEBUG set to true.” This is that test.

The helpers

Why the baseline exists

The previous version ran wp eval 'do_action("init")', which fires init a second time inside an already-booted WordPress. Every registry in core objects, and the procedure reported 123 lines of Block type "core/verse" is already registered as FLOSC findings. Not one came from the plugin. Now the site is exercised twice — plugin off, then plugin on — and only lines appearing solely in the second run are reported.

09 The rulesets

Four config files. None of them hides anything.

phpcs.xml.dist — procedures 3, 5, 6

phpcs-compat.xml.dist — procedure 4

wp-env.json — procedures 10 and 11

"plugins": ["./ship/flosc"] is load-bearing. If that ever reads a path under pre-release-candidates, the container is mounted on a source tree and every tests/ finding is false. doctor checks for exactly that string.

The warning-severity check

Neither PHPCS ruleset sets warning-severity, and neither ever should. doctor reports STALE if it appears — matching the XML element, not the bare word, because the description text in those files explains why there is no such setting and an earlier version flagged the explanation as the offence:

10 doctor

Checking the instrument before trusting the measurement.

An environment that has quietly lost a tool does not go quiet. It reports clean runs on checks that never executed.

Six sections, one line each, OK MISSING STALE, non-zero exit on anything but OK:

SectionWhat it proves
TOOLSphp, composer, node, npx, docker, curl, phpcs, phpstan — present, with versions

The accountability section

INTEGRITY prints the sha256 of flosc-test and every config beside the sha256 of the same file in .flosc-mirror, the read-only git clone. If any coding tool has edited your testing environment on your machine, that difference shows up in one command. Including if the tool was me.

STALE flosc-test local a1b2c3d4e5f6a7b8 != git 9f8e7d6c5b4a3210 — something edited it

Editing flosc-test yourself produces that same line. That is correct: it is telling you the file changed. Commit and push to make it the new baseline.

--fix does only safe, reversible things. It never touches composer globals or configs — it prints the command for those and stops.

11 pull

Refreshing the candidates and the bench itself from GitHub.

Three details worth knowing

  • fetch + reset --hard, never git pull. The mirror is read-only, so there is nothing to reconcile. git pull on a shallow read-only clone stops with “divergent branches” and aborts the rest of your command chain.
  • mv, not cp, for the script itself. mv is atomic and swaps the inode, so the copy currently running keeps its own open file and finishes cleanly instead of executing half of one version and half of another.
  • It warns when .wp-env.json changed. wp-env goes on serving the old configuration until it is restarted. That is how the stale mount happened, so pull now says it at the moment it happens.

The rule that outranks everything here

Do not add a flag that hides findings. --warning-severity=0 once made this suite print 0 for a tree carrying 84 nonce warnings — the exact category WordPress.org rejected you for. A finding that is genuinely not applicable gets a phpcs:ignore with a written reason, in the plugin source, where a reviewer can judge it. Never a flag in the runner, where nobody sees it.

13 What it does NOT check

A suite that does not state its own gaps invites “it passed” to be read as “it is fine”.

  • The reviewers’ AI pass. Every finding marked ✨ in the review emails came from an LLM reading the code. It is non-deterministic: T12 and T13 reviewed the identical zip and returned different lists. Nothing local reproduces it. A clean run here does not predict a clean review.
  • Taint across functions. The T12 SSO finding — an attacker-controlled HTTP_HOST reaching an auth-flow allowlist — crossed three functions. PHPCS is line-scoped and cannot see it. That one was found by reading.
  • That the plugin actually works. Procedure 11 activates it and loads the home page, wp-login.php, a post and a 404 over HTTP, then reports what the plugin added to debug.log. It does not click a button, log in to wp-admin, or hold a conversation.
  • readme.txt external-service documentation. T12 and T13 both raise it and no tool here reads it.
